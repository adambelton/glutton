# 006a — Pending registration

Status: Merged  
Owner: Identity / registration

## Goal

Persist validated pending credentials for direct signup or an existing active guest without creating a user, registering an account or changing access. This is the independently verifiable persistence step before email confirmation and registration UI. Confirmation will upgrade a linked active guest in place or create a RegisteredUser for a direct signup; only then may an email be stored on a User. Depends on task 004's credential rules and task 005's active-guest/session semantics; no other domain contracts are consumed.

Read the implementation plan, product brief (Accounts and privacy), architecture brief (section 11), and root AGENTS.md before implementation.

## Scope

- Add an Identity-owned `PendingRegistration` root model at `app/models/pending_registration.rb`, with a dedicated table, optional guest reference, normalized email, bcrypt password digest and timestamps. Email and credentials stay exclusively in this table until verification. Direct signup creates no User record; an existing guest retains its email-free User record. Keep Rails built-in validation declarations in the model.
- Accept the same email normalization/syntax and password/confirmation requirements as RegisteredUser: canonical email, required password and confirmation, minimum 15 characters and bcrypt's maximum 72 bytes. Use `has_secure_password` with reset-token generation disabled. Do not persist plaintext passwords or password confirmation, and do not expose authentication/session issuance from this record.
- Database constraints require a valid foreign key when a guest reference is present, at most one pending registration per referenced guest, canonical nonblank email and nonblank password digest. Guest lifecycle checks belong in the operation, not a cross-table CHECK or trigger. Pending emails are not globally unique and do not reserve an address: multiple independent requests may use the same address. Null guest references permit multiple direct signups; never deduplicate or associate them by unverified email. Only the eventual confirmed claim may enforce registered email ownership/uniqueness; pending email lookup grants no account access.
- Provide `Identity::PrepareRegistration.call(guest_user_id: nil, email_address:, password:, password_confirmation:)`. For guest signup, the caller must supply its session-bound guest ID, never an email-derived identity. Lock and reload that user; permit only an unexpired GuestUser. Create/replace that guest's pending credentials atomically. With no guest ID, create an independent PendingRegistration without any User or Session record. Return the saved PendingRegistration. Invalid credentials raise `ActiveRecord::RecordInvalid` with the invalid pending record; an explicitly supplied missing/non-guest/expired guest raises a named Identity-owned `RegistrationUnavailable` error with no account details. Unexpected database errors propagate. All failures leave any previous pending credentials untouched.
- Add a runtime-evaluated `GuestUser.active` scope matching the fixed 24-hour predicate and use it for the locked lookup; recheck `active?` after acquiring the lock because waiting can cross expiry.
- A replacement request must supply and validate a fresh password/confirmation; it cannot silently retain the previous digest. Serialize requests for the same guest using its row lock plus the unique database constraint. Recheck current type/expiry before writing; do not trust a cached subtype or `active?` alone to distinguish registered users. No silent transition back from registered/deleted to guest.
- For guest-linked requests, pending validity cannot outlive the original guest deadline (`guest.created_at + 24.hours`); submission/replacement does not extend it. Until confirmation is implemented, only the existing guest session provides access and follows its original expiry. Pending credentials do not authenticate or create a session. For direct signup, pending retention/expiry must be agreed with the confirmation-token lifecycle in task 006b before exposing this operation over HTTP. Eventual cleanup removes guest-linked pending credentials when deleting the expired guest; this task adds only the local association/deletion rule, not a cleanup scheduler.
- Delete PendingRegistration atomically upon successful confirmation in task 006b; retain no completed registration records or status column. Failed confirmation retains the request until expiry. This task does not implement confirmation.
- Filter pending email/password/digest fields from routine logging and record inspection using existing Rails mechanisms. Put any application-authored user-facing validation messages/attribute labels in locale entries. No real addresses or secrets in fixtures/documentation.

## Scope restrictions

- Identity persistence/request preparation only. No Library, Ratings, Recommendations or Film knowledge changes, activity migration or new domain capability abstractions.
- No registration form/routes, email/token issuance, confirmation/resend endpoints, password recovery, guest claim transition, session rotation or uniqueness enforcement across pending requests. These arrive in confirmation and UI tasks; do not expose an unfinished flow to visitors.
- No pending account subtype in users, loosening of registered/guest database constraints, automatic merge, user discovery by email, generic result/integration layer or asynchronous domain communication.
- No new password policy, dependency, provider call, live mail, paid service, deployment or cleanup infrastructure. Do not introduce a separate application-imposed registered-session TTL.
- Implementation is authorized by the owner. Publication and merge remain separate.

## Implementation notes

Implemented PendingRegistration with optional guest FK, normalized email, bcrypt credentials and database constraints; added Identity::PrepareRegistration with guest row locking, validation and atomic replacement, plus RegistrationUnavailable. No UI, email/token issuance or account/session transitions. Applied `bin/rails db:migrate` locally; full CI prepared the test schema. Existing logging filters cover email/password/digest without a new logging abstraction.

Owner decision: unverified email/password information lives in PendingRegistration, not User. Its guest reference is optional, allowing immediate signup without a fabricated guest account. Confirmation creates a registered account for direct signup or upgrades the linked active guest. An expired linked guest fails confirmation; never silently turn that request into direct signup to recover expired activity.

The prior plan combined a registration form with a confirmation flow that did not yet exist. Refine the sequence to pending credential persistence, confirmation/claim capability, then HTTP registration/confirmation wiring. This avoids shipping a form with a dead confirmation link or implying that unconfirmed submission registers the user. All work remains Identity-owned.

Direct pending retention/expiry, token lifetime, replacement-token invalidation, delivery failure handling, confirmation from another browser, claim conflicts and session rotation must be explicitly specified in task 006b before implementation. The UI task must separately specify binding to current_user, request limits, CSRF, non-enumerating responses and failure presentation.
