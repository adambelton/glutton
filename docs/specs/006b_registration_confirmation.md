# 006b — Confirm and complete registration

Status: Merged  
Owner: Identity / verification

## Goal

Turn a valid email-confirmation token into a confirmed registered account and fresh authentication session, atomically consuming its PendingRegistration. Support both direct signup and claiming an active guest in place. Depends on tasks 004, 005 and 006a; consumes no other domain contracts. HTTP/UI delivery wiring remains task 006f.

Read the implementation plan, product brief (Accounts and privacy), architecture brief (section 11) and task 006a before implementation.

## Scope

- Use Rails' existing purpose-scoped signed token primitives for PendingRegistration confirmation. Tokens expire one hour after issuance. Bind token validity to the pending record and a non-sensitive fingerprint of its current email/password digest: changes invalidate old tokens. Signed token payloads are readable; never embed email, password or password digest themselves. Do not add a token table, store plaintext tokens or implement custom signing/cryptography.
- Pending requests have a fixed maximum lifetime of 24 hours from creation. For a guest-linked request, the earlier original guest deadline also applies. Token issuance and completion recheck these deadlines; resending does not extend them. A new valid token cannot revive an expired request. Use runtime predicates/scopes without a stored expiry column. Physical cleanup remains the retention task; expiry alone does not claim deletion has occurred.
- Provide `Identity::RegistrationConfirmation.token_for(pending_registration_id:)` returning a token only for a current eligible request, and `Identity::CompleteRegistration.call(token:)` returning a newly persisted Session on success. Invalid/malformed/wrong-purpose/expired/replaced/replayed tokens, unavailable guests, expired requests and registered-email conflicts raise `Identity::RegistrationUnavailable` with no account details. Unexpected infrastructure/database failures propagate. None of the failure paths authenticates an existing account.
- Issuance performs no delivery, user/session creation or account transition. Multiple issued tokens for an unchanged request may remain valid until their own expiry; the first successful completion deletes the request and invalidates all remaining tokens. Replacement through PrepareRegistration deletes the old pending ID, invalidating its tokens. Email/password changes invalidate tokens through the credential fingerprint. No custom resend-generation counter is needed.
- Completion revalidates the token and current eligibility under database locks. Use a consistent guest-before-pending lock order matching guest preparation; handle a guest reference changing during acquisition by rejecting/retrying safely before writes. Recheck expiry after locks are acquired. Do not trust an earlier token lookup, cached subtype or cached active predicate. Test racing replacement and simultaneous redemption using independent connections.
- Direct signup creates a RegisteredUser with the pending normalized email, existing bcrypt digest and current `email_confirmed_at`. Guest signup transitions the linked active guest to RegisteredUser in place with those values, preserving its ID/created_at and all domain references. Never create a replacement user for an expired/deleted/already registered linked guest; never transfer activity to an existing registered user found by email.
- Transfer only the digest already validated by preparation; do not recover/re-hash plaintext. Provide a narrow, explicitly named/contextual path for creating a confirmed user from validated pending credentials while retaining ordinary RegisteredUser password-on-create rules, other model validations and database constraints. Do not broadly disable validations or weaken guest credential absence/registered credential requirements.
- For a guest claim, revoke all existing sessions owned by that guest so a pre-confirmation cookie cannot silently become registered access. Create exactly one fresh Session for the completed account; direct signup also creates exactly one. Account mutation/creation, guest-session revocation, new-session issuance and pending deletion are one database transaction. Any failure restores the prior pending record, guest state and sessions. This provider returns the Session; it does not set cookies or reset a browser session.
- Enforce email ownership through the existing registered-email unique constraint. Two independent requests for the same address can coexist, but only one may complete. Translate only the expected email uniqueness conflict into RegistrationUnavailable after rollback; do not hide unrelated database errors. Never authenticate, return or merge the existing account on conflict.
- Successful completion deletes PendingRegistration and retains no completed status row or duplicate credentials. Failed completion leaves it available until expiry unless it was independently replaced/deleted by another committed request. Put application-authored user-facing errors/labels in locale entries; keep credentials, recipient addresses and full confirmation tokens out of logs/inspection and exception messages.

## Scope restrictions

- Identity token/completion provider only. No registration form, routes, confirmation landing page/POST handler, cookie binding, browser-session state, reminder UI, rate-limit infrastructure, mail delivery, resend endpoint, password recovery or domain activity changes.
- Task 006f consumes these operations plus the existing AccountMailer contract: generate a link for the exact pending recipient, send outside database transactions, present delivery failure honestly and allow explicit bounded resend. SMTP failure never completes registration. Resend HTTP limits and visible feedback must be specified there before implementation.
- A confirmation token authorizes the exact pending registration independently of the originating browser. HTTP wiring must require an explicit confirmation action (GET does not consume the token), handle an already-authenticated different account without silently switching it, and bind only the returned Session. This task implements neither login UI nor browser policies.
- Do not implement the later direct-signup-to-guest attachment operation here. Preserve the requirement that activity started after signup in the same browser must link through trusted Identity/browser state, never email matching; task 006f must specify locking/conflicts and test it. Account email remains unset until verification.
- No jobs, provider calls, live email, new dependencies, generic integration layer, deployment, cleanup scheduler or automatic retries of account completion. No changes to other domains or global password/session policy.
- Implementation authorized by the owner; publication and merge remain separate.

## Implementation notes

Implemented Rails purpose-scoped confirmation tokens bound to a SHA-256 fingerprint of the pending email/digest, PendingRegistration#active? with fixed expiry, token issuance and atomic completion services. Completion locks guest before pending, revalidates under lock, preserves claimed identity, revokes old guest sessions, returns a fresh Session and deletes the pending row. The explicit `:confirmed_registration` validation context skips only create-scoped plaintext-password presence while retaining common model validations and database constraints; ordinary creation rules are unchanged. Known email uniqueness failures become RegistrationUnavailable after rollback; unrelated failures propagate. No migration, UI, cookie or delivery change. README and architecture documentation updated.

Owner-approved timings: one-hour token and a fixed 24-hour pending request, capped by any linked guest's original deadline. These are registration limits, not registered-session TTLs. Existing confirmation templates make no duration claims and need no new copy solely for these timings.

The plan previously grouped delivery with completion. This task provides the token/atomic transition first; task 006f owns HTTP initiation, link construction/delivery/resend feedback, explicit confirmation action and browser binding. Both remain Identity-owned; no cross-domain integration layer is introduced.

Pending physical retention and guest/activity cleanup remain task 006d and release requirements. Invalidating access does not delete retained credentials. Review direct pending retention cleanup there before public registration is enabled.
