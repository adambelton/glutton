# 006f — Registration and confirmation browser flow

Status: Merged  
Owner: Identity / registration UI

## Goal

A visitor can submit registration credentials, receive a confirmation link and explicitly complete registration in the browser. Preserve an existing guest's identity/activity, including when guest activity starts after direct signup. This is one Identity-owned journey using tasks 005a, 006, 006a and 006b; it changes no product domain.

Read the implementation plan, product brief (Accounts and privacy), architecture brief (section 11), task 006b and root AGENTS.md before implementing.

## Established operations

- `Identity::PrepareRegistration.call(guest_user_id: nil, email_address:, password:, password_confirmation:)` returns a persisted PendingRegistration. Invalid credentials raise RecordInvalid; unavailable guests raise RegistrationUnavailable. A supplied guest ID comes from the current browser identity, never request parameters or email lookup.
- `Identity::RegistrationConfirmation.token_for(pending_registration_id:)` returns an eligible one-hour purpose-bound token. `Identity::CompleteRegistration.call(token:)` returns a fresh Session and atomically consumes the pending record; expected invalid/expired/conflicting claims raise RegistrationUnavailable. It preserves a linked guest ID and revokes all its old sessions.
- `Identity::AccountMailer.confirmation(recipient:, confirmation_url:).deliver_now` composes/sends to the explicitly supplied recipient/link. Delivery exceptions propagate. Use existing UserSessions binding/revocation; browser binding resets the Rails session and registered cookies remain persistent without a custom TTL.

## Scope

### Form, pending page and browser ownership

- Add a registration entry from the home/sign-in screens; a Rails form collects email, password and password confirmation with appropriate labels/autocomplete and localized validation feedback. GET renders only; POST prepares the request. Direct signup creates no User/Session. Existing active guest signup supplies that guest's bound ID. Reject registration while already signed in as a registered user; preserve the existing deleted-account response.
- Remember only the pending registration ID in the encrypted Rails session. Never accept a pending ID from request parameters as ownership proof. Store no email, password/digest or confirmation token in cookies, flash or local storage. Each pending/show/resend request loads the record freshly and checks its lifetime and compatibility with the current identity.
- A new valid submission replaces the browser's previous owned pending request atomically, invalidating its old links. Invalid submission leaves that previous request intact. Supply fresh credentials on replacement. Guest preparation retains its existing guest lock/unique constraint; keep a consistent guest-before-pending lock order in any orchestration. An already consumed or concurrently changed request must not cause an email-derived account lookup or an unintended new guest claim.
- Show a pending page after successful preparation. Make email verification clearly required; do not imply the account or permanent storage already exists. Never render password values back into forms. A missing/expired/replaced/consumed browser reference produces a generic unavailable notice with restart/sign-in options, clears stale pending state, and grants no old activity access.

### Delivery and resend

- Build confirmation links from explicit `APP_ORIGIN` configuration, never an incoming Host header or user-supplied redirect. Require a root HTTPS origin (no credentials, query or fragment) in production; development may use HTTP localhost, including with Resend. Fail clearly for missing/invalid configuration when delivery is requested; document synthetic test values.
- Send only to the normalized email on the exact pending request used to issue the token. Reject new pending requests for already-registered normalized emails with localized sign-in guidance, and send no confirmation. Suppress resend of a stale pending request if its email has since registered. This intentionally exposes registered-email existence through form validation; it grants no account access. Keep the final database uniqueness/conflict guard for races.
- Add an explicit CSRF-protected resend POST. Reserve each mail attempt atomically on PendingRegistration: `confirmation_delivery_attempts` (nonnull integer, default 0, constrained 0–5) and `confirmation_delivery_attempted_at` (nullable timestamp). Initial sending counts toward the maximum of five attempts per request; require at least 60 seconds between attempts. Record attempts before network access, including failed sends, so concurrent clicks/failures cannot bypass the limit. Do not reset counters or extend expiry on resend.
- Commit preparation/attempt reservation before calling SMTP; hold no database locks or transactions during network calls. Show a check-email result only after transport acceptance, explicitly distinct from inbox receipt. On known SMTP/network failure, retain the pending request/browser reference and show a retryable delivery failure without completing registration or echoing provider details. Unexpected programming/database errors must propagate. A delivery failure may consume one attempt. No automatic retries, queue, delivery status tracking or provider-specific error framework.
- Apply Rails request limiting to submission/resend (shared budget: 10 requests per 3 minutes per IP) and confirmation POST (10 per 3 minutes per IP), with localized 429 responses before state mutation. Reuse the current per-worker memory-store approach and document its restart/multiple-worker limitation; no new cache infrastructure. The persistent per-pending mail cap is separate. Distributed abuse controls remain a public-release requirement.

### Explicit confirmation and session binding

- Add a confirmation GET that renders a localized explicit confirmation form, preserving the token only in that form's hidden field. GET, HEAD and link previews never consume tokens, create accounts or sessions, revoke access or send mail. Submit the token through a CSRF-protected POST to CompleteRegistration. Do not require the originating browser's pending reference: the email link works in another browser.
- No current identity: a valid token may complete and bind the returned Session. A current guest may complete only a request linked to that same guest; a direct request should first be attached only when it is also the browser-owned pending request through the continuity rule below. A registered user or an unrelated current guest receives a conflict screen asking them to sign out/open another browser before completing; do not silently switch accounts, attach unrelated activity or consume the token. Recheck policy/state before mutation using consistent Identity locking, without weakening CompleteRegistration's token/lifecycle guards.
- On success bind only the provider-returned Session through UserSessions, clearing pending browser state and rotating Rails session/CSRF state. Redirect to the existing home page with localized confirmation success. Do not expose arbitrary return URLs. Preserve existing cookie HttpOnly/SameSite/production Secure settings and server-side revocation.
- Invalid, expired, replaced, replayed or email-conflicting links get the same localized unavailable result without account details; retain any current identity and offer sign-in/restart. Show the existing deleted-account failure until explicit sign-out.

### Continuity while awaiting verification

- Add an Identity-owned attachment operation invoked by `ensure_guest_user!` when personal activity creates a guest and this browser owns an eligible direct pending request. Do not create a guest just for visiting the registration/pending page. Preserve the pending ID, email/digest and already-issued tokens; adding the guest reference must not invalidate a link that already reached the inbox. Its effective lifetime becomes the earlier of original pending expiry and the guest's original deadline.
- Lock the guest before pending, reload both, and permit only an active guest and active unlinked request. An existing link to this same guest is idempotent. A different guest link or another pending request already attached to the new guest is a conflict: never overwrite, merge or infer identity by email. Roll back new guest/session creation on a genuine attachment conflict; propagate unexpected persistence errors. Expired/missing pending state is cleared with an explicit unavailable notice rather than attached or revived. Confirmed/registered identities must never be treated as new guests by this path.
- `bind_session` currently resets Rails session state. Preserve the validated pending reference across guest binding only, so that first guest creation does not lose it. Registered sign-in, confirmation success and explicit sign-out clear pending browser state without deleting another account or transferring activity.
- Show a persistent verification reminder on existing app pages while a current pending request exists. Show the actual effective pending deadline and, once a guest exists, its temporary-activity expiry. Localize text and time formatting. Do not extend deadlines, claim unconfirmed progress is permanent, or hide an expired request behind a success notice.
- Verify signup → first guest activity → confirmation using a test-only controller calling the existing Identity concern, as in prior session tests. There is no production ratings/library action yet; do not invent a production guest-creation or diagnostic endpoint just to demonstrate this flow.

## Scope restrictions

- Identity only: no Ratings/Library/Recommendations/Film knowledge records, controllers, navigation or activity writes. First real rating wiring remains its later owning-domain task using Identity's existing entry point.
- Keep current credential, token, guest expiry and registered-session policies. No alternate authentication provider, OAuth, password recovery, email changes for registered users, account deletion or automatic guest/account merge.
- No new frontend/design framework, generic workflow/integration layer, background jobs, webhook, cleanup scheduler, paid service, DNS changes or deployment. Pending/guest retention cleanup remains task 006d and a release requirement.
- Use small Rails CRUD controllers/actions, views and the existing mailer/Identity operations. New application copy belongs in locale files, with strict missing-key checks; use explicit `.nil?`/`.present?` existence checks. Preserve model layout and keep domain coordination out of templates.
- Add `Cache-Control: no-store` and `Referrer-Policy: no-referrer` for registration/confirmation pages. Keep token/email/password fields and full token-bearing URLs out of routine logs; confirm filtering covers request paths as well as parameters. Do not include tokens in third-party resources, exception messages or analytics.
- Implementation authorized by the owner. External communication, live mail, publication and merge remain separate. Automated delivery uses test transport/intercepted SMTP. Optional manual Resend verification requires an explicitly designated test recipient and usable trusted HTTPS origin; record acceptance/receipt separately and do not claim unrun checks passed.

## Implementation notes

Implemented registration/show/resend/confirmation controllers and localized views, explicit trusted-origin email links, atomic per-pending attempt reservation, browser-policy completion, direct-request replacement and guest attachment operations. UserSessions preserves validated pending state across guest binding only and clears it for registered binding/sign-out. Persistent verification/expiry reminders include an explicit stale-state notice; that notice survives guest session rotation. Known network failures retain retryable state, and exhausted requests offer existing-link/restart choices. Added the delivery counter/timestamp migration and database bounds; ran `bin/rails db:migrate` locally. No new dependencies, product-domain changes or deployment.

Owner-approved limits: five delivery attempts per pending request, at least 60 seconds apart, plus the existing style of per-IP/per-worker Rails rate limits. Failed sends count as attempts; transport acceptance is not an inbox guarantee. New valid registration submissions create replacement requests and invalidate old tokens, so the IP budget also applies to initial submissions.

The signup/activity continuity requirement is implemented here within Identity's existing guest/session concern and an attachment operation; it does not require modifying product domains. No actual activity can be saved by the present home page; tests demonstrate the established Identity entry point without broadening product scope.

The current token/completion APIs remain authoritative. Any necessary guard/helper for browser identity or atomic attachment stays narrowly Identity-owned and must preserve their existing tests/contracts. Do not silently expand to general account management or a new integration framework.
