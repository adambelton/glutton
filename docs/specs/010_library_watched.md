# 010 — Canonical Library watched state

Status: Ready for review  
Owner: Library / viewing

## Goal

Record one canonical watched relationship for an active user's existing film and expose an idempotent operation/read result. Depends on task 005a's session-bound current identity and task 007's Film persistence. No Ratings or Recommendations contract is consumed. This is Library's provider capability; future consuming workflows remain tasks 016/017.

Read the implementation plan, product brief sections 2 (Accounts and privacy), 3.3 and Ownership of viewer activity, architecture brief sections 4/11, and task 006d's retention restrictions before implementation. The owner approved the retention boundary below with this spec before implementation.

## Scope

### Persistence and watched invariant

- Add LibraryFilm as the concrete Rails STI root, backed by library_films, with LibraryFilmWatched < LibraryFilm as the only subtype implemented in this task. Use top-level files app/models/library_film.rb and app/models/library_film_watched.rb, default Rails table/STI naming, and no namespace, abstract-class flag or Zeitwerk collapse.
- Store internal ID, type, user_id, film_id, watched_at and timestamps. Require existing owner/film references. Enforce one relationship per user/film across all STI types with base-model validation and a unique database index on (user_id, film_id), not (user_id, film_id, type); enforce references with foreign keys.
- Persist only LibraryFilmWatched rows in this task, with type=LibraryFilmWatched and non-null watched_at enforced by model/database constraints. LibraryFilm is a query/invariant root, not an additional unclassified persisted state: direct base-row creation must fail. No row represents an unclassified film. Future subtype tasks will explicitly revise the allowed-type and timestamp constraints.
- LibraryFilm owns shared user/film identity invariants; LibraryFilmWatched owns watched-specific invariants and behaviour. Future names are LibraryFilmToWatch and LibraryFilmNotInterested, but do not add placeholder classes or their behaviour in task 010. STI is justified by distinct constraints/actions and controlled transitions, not merely folder organisation. Do not add a parallel status/intent column duplicating type, rating columns, history tables or generic state-machine machinery.
- Persisted relationship state is produced by the concrete Library subtype. FilmState distinguishes absence from a relationship, but must not infer watched classification from row existence; RecordWatched delegates its result to the subtype as well. Do not introduce future transition hooks or placeholder implementations to anticipate later types.
- watched_at records when Glutton first successfully recorded watched confirmation, using server time; it is not a user-supplied claim about the actual viewing date. Repeated record-watched calls preserve the entry ID, watched_at and unchanged-row timestamps. Different users may classify the same film independently.
- Keep film identity/metadata with Film knowledge. A LibraryFilm is private viewer activity and supplies no rating, expression or inferred preference. Do not add Library associations/callbacks to User or Film; LibraryFilm may reference those existing models from its owning domain.

### Agreed synchronous provider contracts

Owner approved these contracts before implementation; later consumer tasks must call them without modifying Library internals.

- `Library::RecordWatched.call(user:, film:)` accepts the persisted current-user model supplied through Identity and a persisted film model. Treat these as internal behavioural contracts rather than guarding their concrete Ruby classes. Never accept a TMDB ID or arbitrary caller-supplied owner ID as a substitute. Nil/unpersisted models are unavailable; validate persisted record existence internally without explicit User/Film class checks. A programmer passing an object that does not implement the model protocol gets the ordinary Ruby method error, not a defensive argument-type wrapper. Re-read the actor from the database under its user-row lock and check the established active? predicate before accessing/writing private state; do not trust a stale in-memory guest/account lifecycle.
- Return a plain hash `{ film_id:, classification: :watched, watched_at: }`, using the persisted first-recorded timestamp. Create a LibraryFilmWatched only if the user/film relationship is absent; query uniqueness through LibraryFilm, not just the subtype. Repeated/concurrent calls for the same actor/film converge on one entry and the same result, rather than resetting timestamps or treating an already-watched film as an error.
- `Library::FilmState.call(user:, film:)` returns `{ film_id:, classification: :watched, watched_at: }` or `{ film_id:, classification: :unclassified, watched_at: nil }` for an existing film, scoped solely to the resolved active user. It performs no writes. Use the same fresh actor validation; a read does not bypass expiry or inactive-account rejection.
- Missing/unpersisted/deleted/inactive actors raise Library::IdentityUnavailable, including exactly-at-24-hours guests. Use nil-safe behavioural checks (such as user&.persisted? and the fresh owner&.active?), not is_a?/instance_of? checks. No presence wrapper is needed for models. Resolve the actor before the film so unauthorized callers gain no film/private-state information. Nil, unpersisted or physically missing films raise Library::FilmUnavailable without creating/importing a film; do not trust a stale supplied Film object. Unclassified is a successful read, not an exception.
- All writes occur in one local database transaction. Lock the user before any Library row; validate the fresh actor while holding that lock, then lock/create the user/film entry. Coordinate with established Identity user-row locking without changing Identity code. No provider/network calls occur inside the transaction. Persistence/constraint failures propagate and roll back the operation; no automatic retries or success-shaped fallback. Calls inside a future caller transaction must remain rollbackable with that transaction, enabling task 016's separately specified consumer consistency.
- Never look up entries solely by a request-supplied entry ID. Foreign-user entry IDs are not inputs; one actor cannot read/change another user's relationship. Do not create a guest or session here: the later HTTP caller obtains its trusted identity through Identity first.

### Guest retention: approved boundary decision

- Library entries have no independent reason to survive physical removal of their owning user. Approved policy: physically delete these dependent rows in the same transaction as that user's physical deletion, retain shared Film records, and retain entries when an active guest is claimed in place as a registered user. Guest expiry still revokes access immediately; physical removal remains eventual.
- Approved mechanism: Library declares a narrowly scoped `ON DELETE CASCADE` foreign key from library_films.user_id to users.id. Film references remain restrictive. This is a Library-owned dependent-data invariant, not a global cascade, asynchronous domain communication or generic deletion coordinator. It requires no new Identity operation/callback: existing cleanup already deletes a freshly locked/rechecked expired guest in one transaction, while claiming preserves the user's ID.
- The owner reviewed and approved this scoped invariant against task 006d's requirement to agree product-activity deletion before persistence. It does not authorize relaxing other foreign keys or bypassing cleanup failures. If boundary review instead establishes that deletion has independent Library rules requiring an operation, revise this spec and agree explicit provider/consumer work before implementation; do not add hidden Identity changes here.
- Verify real compatibility by calling established Identity cleanup/claim operations from Library-owned tests without changing their implementation. A rollback of user deletion must restore Library entries alongside Identity rows; cleanup that loses a claim race must preserve the new registered identity and its entries. Cleanup output/count contracts remain unchanged. Its bounded candidate count does not bound the number of dependent entries deleted for an individual guest; document that operational limit honestly.
- No registered-account deletion workflow or retention policy is implemented. Existing registered/deleted users are not selected by guest cleanup. This entry policy is not a blanket policy for future Ratings/Recommendations records.

## Scope restrictions

- Library only. No modifications to Identity, Film knowledge, Ratings or Recommendations implementations, their models, callbacks or UI. Calling existing identity/film persistence contracts and verifying compatibility is allowed; a required change in another domain needs separate ownership review/specification.
- No HTTP/controller/view/navigation work, watched list, watchlist, dismissal, unwatch, date editing, rewatch/history or public API endpoint. Tasks 011/012 introduce LibraryFilmToWatch/LibraryFilmNotInterested and their allowed transitions; tasks 017/020 introduce workflow/view behaviour. Those later specs must define preservation of independent watched facts before implementing transitions; changing STI type must not silently erase viewing history.
- Do not add a cross-type transition API or instantiate future types in this task. Once those types are introduced, permitted transitions must be explicit and transactional, preserving the same relationship ID and uniqueness invariant. They must not be implemented through unrestricted caller-supplied type assignment or an automatic destroy/recreate convention.
- No Ratings selection, rating submission/current-rating lookup, make-available calls or queuing. Saving watched does not imply a completed rating. Library subtype behaviour must not be used as a new prerequisite imposed on Ratings: the agreed Ratings operation accepts a rating without a watched Library record and records watched only on completion. Future Library UI may expose actions appropriate to its type; that does not relocate rating persistence or change the Ratings contract. This primitive must not trigger Ratings; task 017 owns that consuming workflow and task 016 records watched after rating without requeueing.
- Review existing application class checks read-only for comparable internal argument guards; retain external HTTP/JSON/configuration validation, schema-shape checks and targeted exception recovery. Do not change other domains or replace Identity lifecycle-policy branches under this Library task. Record findings rather than broadening implementation scope.
- No TMDB calls/import, AI/JEV, jobs/events, generic integration/retention framework, scheduler, paid service, deployment, publication or merge. No development/production data writes during verification; use isolated test records/databases.
- Use Rails locale entries and symbolic model validation errors for new application-authored validation text. Developer-only exceptions remain static diagnostics; there is no new application UI copy.

## Implementation notes

Implemented LibraryFilm/LibraryFilmWatched, the constrained library_films table, scoped user-delete cascade, restrictive film reference and root uniqueness index. RecordWatched and FilmState share the small Library-local FilmAccess helper for nil/persistence checks, fresh active identity checks and user-before-relationship lock ordering. Read/write results match the approved contracts; no Ratings calls or model callbacks were added to other domains.

Owner selected the model/STI naming and approved the dependent-row retention policy before implementation. Existing Identity claim/cleanup operations are used unchanged and tested for compatibility. The per-user cascade retains no independent activity and needs no new Identity consumer operation. Future independent domain deletion rules still require boundary review; this is not a general retention framework.

Owner-directed contract revision: operations accept user: and film: model collaborators, not film_id:. Removed the concrete User class guard and primitive film-ID guard; nil-safe persisted? checks and the fresh locked owner&.active? predicate retain the agreed lifecycle semantics. No presence wrapper or new Film class guard was added. A SimpleDelegator-based test verifies model collaborators need not inherit from User/Film, while stale actor/film and concurrency/retention tests still pass. README and contracts reflect the new arguments.

Read-only class-check audit covered app/ with is_a?, instance_of?, kind_of?, .class and respond_to? searches. That initial audit was too narrowly framed around argument guards and did not assess misplaced subtype behaviour. A separate Identity behaviour audit is scheduled after this task merges. Remaining checks fall into external request/token/credential/provider payload validation, JSON metadata shape, bounded cleanup configuration, or targeted exception recovery (Film import duplicate handling and Identity registration errors). These remain in place. Identity controllers/views also branch on UserGuest/UserRegistered/UserDeleted for session, registration and recovery policy. Those are behavioural dispatch candidates for a future Identity-owned polymorphism review, not removable argument guards; this task changes no Identity implementation. The architecture brief records the internal behavioural-contract convention.

README, product/architecture briefs and plan document Library activity retention, operation use and limits. LibraryFilmToWatch/LibraryFilmNotInterested and all transitions beyond initial watched creation remain deferred. Guest candidate bounds do not bound dependent Library rows per guest; scheduler deployment and registered-account deletion remain outside scope.
