# Ratings event publication — version 1

Task 014 publishes first rating submissions. It adds no subscribers; Library and Recommendations will implement their own consumers in separately approved tasks.

## Meaning and payload

`Ratings::EVENTS_PUBLISHING_DOMAIN` is `ratings`. `Ratings::Events::RATING_SUBMITTED` is `RatingSubmitted`, schema version **1**.

The fact means the owner explicitly completed a rating and therefore supplies viewing evidence. It does not mean Library has already updated, and it is not generated by selection, dismissal or a Library fact.

The JSON payload has exactly these keys:

| Key | Meaning |
| --- | --- |
| `user_id` | Stable internal owner ID |
| `film_id` | Shared internal Film ID |
| `rating_id` | Persisted Rating ID |
| `value` | One of `brilliant`, `enjoyed`, `not_for_me`, `garbage` |

Values are rating choices, not numeric preference weights. Localized display labels belong in `config/locales/ratings.en.yml`. No expressions, credentials or serialized model data are included. Version 1 is immutable; incompatible changes require a new schema version.

## Source operation and atomicity

`Ratings::SubmitRating.call(user_id:, rating_film_id:, value:)` accepts an existing owned candidate and returns the saved Rating. It locks the fresh active owner, then the candidate. The model owns submission permission and creation. The operation publishes through the established `DomainEvents::Publish` contract within the same savepoint.

Missing/inactive owners raise `Ratings::IdentityUnavailable`; absent/foreign candidates raise `Ratings::FilmUnavailable`. A previously rated candidate raises `Ratings::AlreadyRated`, even for an identical value. Invalid input raises `ActiveRecord::RecordInvalid`; validation checks the original choice before string coercion. First-submission uniqueness and required valid values/references are also database constraints.

A dismissed candidate may be explicitly rated. Its dismissal and creation time remain unchanged; automatic selection uses `pending` (unrated and not dismissed). No Library change is performed synchronously. Rating revisions, edits and `RatingRevised` publication are reserved for task 023, which must explicitly revise first-submission uniqueness and settle current/history semantics.

Validation failure, publication failure or caller rollback leaves neither a rating nor its event. After-commit wake failure follows Foundation's durable recovery contract; it does not undo committed source activity.

## Stream and delivery

Stream identity is `(user_id, publisher: "ratings", stream_key: "film:<internal film ID>")`, independent of candidate/rating row IDs. Foundation allocates monotonic stream sequences and event UUIDs. `occurred_at` records publication time. Direct submissions start their own correlation (event ID) with no causation ID.

Delivery is at least once, ordered within a subscriber's stream, with independent consumer transactions and receipts. There is no total ordering against Library streams. Future consumers must define supported schemas, retained-event bootstrap, duplicate handling and contradiction resolution before implementation. An event retry must not be treated as another user submission. No subscriber or synchronous fallback is installed by this task.

## Ownership and retention

Guest claim keeps the owner, candidate, rating and event/stream identities. Expired/deleted owners cannot submit. Physical owner cleanup cascades candidates, ratings and the existing Foundation event storage; shared Film rows remain. Film references stay restrictive while a candidate exists. No age-based event purge or new retention schedule is introduced.
